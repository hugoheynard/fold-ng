The date model the calendar family is built on: a FoldCalendarDate is a plain YYYY-MM-DD string, not a Date. Everything here is pure — the only function that reads a clock is foldToday().

why not a Date

A calendar of all-day spans deals in dates, not instants. new Date("2026-05-18") is UTC midnight — which is the 17th anywhere west of Greenwich, so the same span lands on a different cell depending on where the browser is. A string removes that whole bug class by construction.

It buys three things on top:

  • values compare lexicographically — a <= b is “on or before”, so a range test is a string comparison;
  • two dates meaning the same day are === equal (two Dates never are);
  • it is already the wire format a backend sends.

Arithmetic runs through Date.UTC, never local time: UTC has no DST, so a day is always exactly 86 400 000 ms. fold-timeline keeps a native Date on purpose — it plots dated instants, which is the other domain.

localisation

Month and weekday names are not in the label token: the calendar reads them from Intl.DateTimeFormat, driven by its locale input, so every locale comes for free instead of twelve hand-translated month names.

Bridge a plain date to Intl with foldToNativeDate(), which lands on UTC midnight — format it with timeZone: "UTC" or the local zone shifts the label back a day.

FoldCalendarLabels covers only what Intl cannot supply: the today marker, the “+N more” chip and the event count.
